Flagchecker

To make the CTF easier for you, we provide you with a flag checking binary.

CTF를 더 쉽게 풀 수 있도록 플래그 검사 바이너리를 제공합니다.

ATTACHMENTS
FLAG FORMATgctf{.*}

Write Up

Starting from the Challenge

Extracting flagchecker.tar.gz gives this directory:

flagchecker/
├── challenge
└── sha256sum

The challenge description says, “To make the CTF easier for you, we provide you with a flag checking binary.” challenge is the Linux executable that checks an entered flag, and sha256sum records its SHA-256 hash. I confirmed that the executable matches the supplied checksum, then examined what input would pass its check. All commands below run from the flagchecker directory.

1. Finding the checker

I checked the symbol table for a place to start tracing the input.

objdump -t ./challenge

The relevant entries are main, a function, and flags, a large data region beginning at 0x402020.

0000000000401186 g     F .text   00000000000002e0  main
0000000000402020 g     O .rodata 000000000014e400  flags

I disassembled main to see whether it reads the input and uses flags.

objdump -d -M intel --disassemble=main ./challenge

# challenge — challenge file (excerpt)
401360: call 401050 <fgets@plt>
# ...
4013a6: xor eax,0x12
# ...
4013fb: mov rax,QWORD PTR [rbp-0x18]
4013ff: shl rax,0x8
401403: mov rcx,rax
401406: mov rax,QWORD PTR [rbp-0x20]
40140a: add rax,rcx
40140d: mov eax,DWORD PTR [rax*4+0x402020]
401414: xor eax,edx
401416: xor DWORD PTR [rbp-0x4],eax
# ...
40142b: cmp DWORD PTR [rbp-0x4],0x0

main reads the input, XORs each character value with 0x12, and checks it against rows of flags. The address calculation selects one of 256 four-byte values in a row. For each row, the checker XORs the transformed input with the corresponding array values and accumulates the results. A row whose accumulator is zero passes.

2. Recovering strings from flags

The symbol size 0x14e400 equals 1,337 rows of 256 four-byte values. To read those values from the file, I located the section containing flags.

readelf -W -S ./challenge | grep '\.rodata'

[15] .rodata PROGBITS 0000000000402000 002000 14e466 00 A 0 0 32

.rodata begins at virtual address 0x402000 and file offset 0x2000. Since flags starts 0x20 bytes into that section, its file offset is 0x2020. Each row stores character values at the front and zeros in the remaining slots. XORing the first row's values 74 7e 75 69 with 0x12 gives flg{. Other rows produce similar strings, so I searched for the required gctf{...} format.

# solve.py — written for this write-up
from pathlib import Path
import struct

data = Path("./challenge").read_bytes()
values = struct.unpack_from("<342272I", data, 0x2020)

matches = []
for i in range(1337):
    row = values[i * 256 : (i + 1) * 256]
    decoded = bytes(x ^ 0x12 for x in row if x)
    if decoded.startswith(b"gctf{") and decoded.endswith(b"}"):
        matches.append((i, decoded.decode()))

assert len(matches) == 1
print(matches[0])

The only matching row is 706.

(706, 'gctf{cf776a78f2488869cebfefd87a3e6a9fd582b9e556d0779216c5bb5b45ea4a70}')

3. Checking the recovered flag

A first attempt through a PowerShell pipeline failed because it appended 0d 0a. The checker stops at 0a, leaving 0d as an extra input character. Sending only LF succeeds.

printf '%s\n' 'gctf{cf776a78f2488869cebfefd87a3e6a9fd582b9e556d0779216c5bb5b45ea4a70}' | ./challenge

Enter flag:
The flag is valid!

Final Flag

gctf{cf776a78f2488869cebfefd87a3e6a9fd582b9e556d0779216c5bb5b45ea4a70}

Summary

  • Checker: main transforms input with 0x12 and compares it against rows of flags.
  • Recovery: Decoding all 1,337 rows yields one string in the required format, at row 706.
  • Verification: The recovered string passes the supplied checker when sent with LF.

문제에서 출발하기

flagchecker.tar.gz를 풀면 다음과 같은 디렉터리가 생긴다.

flagchecker/
├── challenge
└── sha256sum

문제는 “To make the CTF easier for you, we provide you with a flag checking binary.”라고 설명한다. challenge는 입력한 플래그를 검사하는 Linux 실행 파일이고, sha256sum에는 이 파일의 SHA-256 해시가 적혀 있다. challenge의 해시가 배포값과 일치하는 것을 확인한 뒤, 어떤 입력이 검사를 통과하는지 살펴봤다. 아래 명령은 모두 flagchecker 디렉터리에서 실행했다.

1. 검사 코드 찾기

입력을 처리하는 함수를 찾기 위해 심볼 표부터 확인했다.

objdump -t ./challenge

눈에 띄는 항목은 함수 main과 0x402020에서 시작하는 큰 데이터 flags다.

0000000000401186 g     F .text   00000000000002e0  main
0000000000402020 g     O .rodata 000000000014e400  flags

main이 실제로 입력을 읽고 flags를 사용하는지 확인했다.

objdump -d -M intel --disassemble=main ./challenge

# challenge — challenge file (excerpt)
401360: call 401050 <fgets@plt>
# ...
4013a6: xor eax,0x12
# ...
4013fb: mov rax,QWORD PTR [rbp-0x18]
4013ff: shl rax,0x8
401403: mov rcx,rax
401406: mov rax,QWORD PTR [rbp-0x20]
40140a: add rax,rcx
40140d: mov eax,DWORD PTR [rax*4+0x402020]
401414: xor eax,edx
401416: xor DWORD PTR [rbp-0x4],eax
# ...
40142b: cmp DWORD PTR [rbp-0x4],0x0

main은 입력한 문자열의 각 글자 값을 0x12와 XOR한 뒤 flags의 여러 행과 대조한다. 주소 계산을 보면 한 행에는 4바이트 값이 256개 있다. 각 행에서 변환된 입력과 같은 위치의 배열 값을 XOR하고 결과를 누적한다. 누적값이 0인 행을 만나면 검사를 통과한다.

2. flags에서 문자열 복원하기

심볼 표에 나온 flags의 크기 0x14e400바이트는 4바이트 값 256개로 된 행 1,337개에 해당한다. 파일에서 배열을 읽으려면 시작 오프셋을 알아야 한다.

readelf -W -S ./challenge | grep '\.rodata'

[15] .rodata PROGBITS 0000000000402000 002000 14e466 00 A 0 0 32

.rodata는 메모리 주소 0x402000, 파일 오프셋 0x2000에서 시작한다. flags는 이 영역의 시작보다 0x20바이트 뒤에 있으므로 파일 오프셋은 0x2020이다. 각 행의 앞부분에 글자에 해당하는 값이 있고 남은 칸은 0이다. 첫 행의 값 74 7e 75 69를 각각 0x12와 XOR하면 flg{가 나온다. 다른 행에도 비슷한 문자열이 있어, 모든 행을 복원한 뒤 플래그 형식 gctf{...}에 맞는 것을 찾았다.

# solve.py — written for this write-up
from pathlib import Path
import struct

data = Path("./challenge").read_bytes()
values = struct.unpack_from("<342272I", data, 0x2020)

matches = []
for i in range(1337):
    row = values[i * 256 : (i + 1) * 256]
    decoded = bytes(x ^ 0x12 for x in row if x)
    if decoded.startswith(b"gctf{") and decoded.endswith(b"}"):
        matches.append((i, decoded.decode()))

assert len(matches) == 1
print(matches[0])

형식에 맞는 문자열은 706번 행에서 나왔다.

(706, 'gctf{cf776a78f2488869cebfefd87a3e6a9fd582b9e556d0779216c5bb5b45ea4a70}')

3. 검사기로 확인하기

처음 PowerShell 파이프로 전달한 입력에는 줄 끝에 0d 0a가 붙어 실패했다. 검사기는 0a에서 입력을 끊으므로 앞의 0d가 한 글자로 남는다. LF만 붙여 다시 전달하자 성공했다.

printf '%s\n' 'gctf{cf776a78f2488869cebfefd87a3e6a9fd582b9e556d0779216c5bb5b45ea4a70}' | ./challenge

요약

  • 검사: main이 입력을 0x12와 XOR해 flags의 행들과 비교한다.
  • 복원: 1,337개 행 중 706번 행에서 플래그 형식에 맞는 문자열이 나왔다.
  • 확인: LF로 입력한 문자열이 배포 검사기를 통과했다.
