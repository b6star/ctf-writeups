Frostgate License Manager

Our new license manager is unbreakable. Find a valid license key. (Tested under wine & Windows)

새 라이선스 관리자는 절대 뚫을 수 없습니다. 유효한 라이선스 키를 찾으세요. (wine과 Windows에서 테스트됨)

ATTACHMENTS
FLAG FORMATgctf{.*}

Write Up

Starting from the Challenge

Frostgate asks for a valid license key. Extracting virt.tar.gz gives the following directory.

virt/
├── virt.exe
└── sha256sum

sha256sum contains the distribution hash for virt.exe. From the virt directory, I checked what kind of program I had.

file ./virt.exe

./virt.exe: PE32+ executable for MS Windows 4.00 (console), x86-64 (stripped to external PDB), 8 sections

It’s a 64-bit Windows console program. I ran it and entered a trial key in the contest’s flag format.

./virt.exe

=====================================
   Frostgate License Manager  v3.1
=====================================
Enter license key: gctf{AAAAAAAA}
Checking license, please wait...

[-] Access denied.

The key was rejected. If the program also printed a message on success, the code that printed it would lead back to the check. I searched for the ] Access part of the rejection.

strings -a ./virt.exe | grep -F '] Access '

[+] Access granted. The key you entered is the flag.
[-] Access denied.

The success message confirms that the accepted key itself is the flag.

1. Where does the program print success?

I located the message in .rdata, where the executable stores its string constants.

objdump -s -j .rdata ./virt.exe | grep -F -A 3 '[+] Access'

10001b360 350a5b2b 5d204163 63657373 20677261  5.[+] Access gra
10001b370 6e746564 2e205468 65206b65 7920796f  nted. The key yo
10001b380 7520656e 74657265 64206973 20746865  u entered is the
10001b390 20666c61 672e0000 130a5b2d 5d204163   flag.....[-] Ac

The message record starts at 0x10001b360: 35 is its length byte, 0a is a newline, and the visible [+] text begins two bytes later. I searched the disassembly for the record's starting address.

objdump -d -M intel --no-show-raw-insn ./virt.exe > virt.asm
grep -F '0x10001b360' virt.asm

100012551: lea r8,[rip+0x8e08]  # 0x10001b360
10001264e: lea r8,[rip+0x8d0b]  # 0x10001b360

Both instructions load the success-message address. To see which checks lead to them, I expanded the code around each reference. The addresses below are the two references just found.

grep -B 55 -A 30 '100012551:' virt.asm
grep -B 40 -A 30 '10001264e:' virt.asm

The relevant lines from the two larger outputs are:

10001248c: ret
1000124a4: cmp DWORD PTR [rip+0x13c65],0x28  # 0x100026110
100012533: cmp DWORD PTR [rbp-0x10],0x0
100012551: lea r8,[rip+0x8e08]  # 0x10001b360
1000125b0: ret
1000125d4: cmp DWORD PTR [rip+0x13b35],0x27  # 0x100026110
10001263e: cmp DWORD PTR [rbp-0x8],0x0
10001264e: lea r8,[rip+0x8d0b]  # 0x10001b360
1000126ad: ret

After the previous function's ret, the first check compares the input length at 0x100026110 with 0x28 (40), checks the accumulated result, and can use the success message before its own ret. The following check compares the same length with 0x27 (39) and can use that message too. I read the 39-byte check first.

2. What does the 39-byte check accept?

I expanded the code above the 39-byte check's success-message reference to read its comparison loop.

grep -B 50 '10001264e:' virt.asm

The relevant lines are:

1000125fd: imul eax,eax,0x2f
100012600: lea eax,[eax+0xa7]
100012612: lea rdx,[rip+0x7277]  # 0x100019890
100012619: movzx ecx,BYTE PTR [rdx+rax*1]
10001261d: xor ecx,DWORD PTR [rbp-0xc]
100012623: lea rax,[rip+0x13aa6]  # 0x1000260d0
10001262a: movzx eax,BYTE PTR [rax+rdx*1]
10001262e: xor ecx,eax
100012630: or ecx,DWORD PTR [rbp-0x8]

This check goes through all 39 input characters. At position i, it calculates (47 * i + 167) & 0xff using the constants 0x2f (47) and 0xa7 (167) from the checker. It XORs that result with the ith byte of the table starting at 0x100019890, then compares it with the ith input character. Any mismatch is recorded. The accepted character at every position is therefore table[i] ^ ((47 * i + 167) & 0xff). I read the table to recover all 39 characters.

objdump -s ./virt.exe | grep -F -A 2 '100019890'

 100019890 d0a46a5a 04e9a7c1 717a119d a1394b37  ..jZ....qz...9K7
 1000198a0 f3f59614 2adddfd0 7b6119f4 f8a55b6b  ....*...{a....[k
 1000198b0 b3daba24 2d41dc00 00000000 00000000  ...$-A..........

These three lines contain the 39 table bytes used by the check. I applied the position-dependent calculation and XOR to each byte.

# decode_decoy.py — written for this write-up
table = bytes.fromhex(
    "d0a46a5a04e9a7c1717a119da1394b37"
    "f3f596142adddfd07b6119f4f8a55b6b"
    "b3daba242d41dc"
)
print(bytes(value ^ ((47 * i + 167) & 0xff)
            for i, value in enumerate(table)).decode())

wrong{f1n4l1z3r_d3c0y_n0t_th3_r34l_0n3}

The string calls itself a decoy and starts with wrong{. The contest expects gctf{, so I went back to the other function that prints the success message.

3. Recovering the key one character at a time

The other success-message reference was at 0x100012551. I read upward from there to its loop.

grep -B 65 '100012551:' virt.asm

The relevant lines are:

1000124a4: cmp DWORD PTR [rip+0x13c65],0x28  # 0x100026110
1000124be: xor eax,0xdeadbeef
1000124ef: call 0x100012340
1000124f4: mov DWORD PTR [rbp-0xc],eax
1000124fa: lea rdx,[rip+0x735f]  # 0x100019860
100012501: movzx eax,BYTE PTR [rdx+rax*1]
100012505: xor eax,DWORD PTR [rbp-0xc]
100012508: or eax,DWORD PTR [rbp-0x10]
100012523: call 0x100012410
100012528: mov DWORD PTR [rbp-0x8],eax

For each character, the first called function takes the input byte, the current state and the position. Its result is compared with the table at 0x100019860. The second function uses that input byte to update the state for the next position.

A mismatch sets a bit in the accumulated result, and the or keeps it set. Every position therefore has to match. Before the loop, the program initializes the state to the input length XOR 0xdeadbeef, so the starting value is known. That gives a way to test the first character on its own. Once it matches, the second function gives the state needed to test the next one.

Both functions run their calculations through the virtual machine in .frost0. I used the functions already in the binary. To reach this loop in GDB, I used an analysis copy with the selector fixed to the 40-byte checker and supplied a 40-byte trial key. At the first call in the loop, I ran the following Python code in GDB to try each printable ASCII character.

# recover.gdb — written for this write-up (Python excerpt)
import gdb
target = bytes(gdb.selected_inferior().read_memory(0x100019860, 40))
state = 0xDEADBEC7
flag = bytearray()
for i, want in enumerate(target):
    matches = []
    for ch in range(32, 127):
        result = int(gdb.parse_and_eval(
            "((unsigned int (*)(unsigned int,unsigned int,unsigned int))"
            "0x100012340)(%d,%d,%d)" % (ch, state, i)
        )) & 0xFF
        if result == want:
            matches.append(ch)
    if len(matches) != 1:
        raise RuntimeError("position %d has candidates %r" % (i, matches))
    ch = matches[0]
    flag.append(ch)
    state = int(gdb.parse_and_eval(
        "((unsigned int (*)(unsigned int,unsigned int,unsigned int))"
        "0x100012410)(%d,%d,%d)" % (state, ch, i)
    )) & 0xFFFFFFFF
print("FLAG " + flag.decode("ascii"))

FLAG gctf{I_h4t3_d3lph1_4nd_n0w_h0pefully_u2}

At the first position, only g produced the table’s first byte, 0x2e. Each remaining position also had a single match.

4. Checking the key in the original program

I passed the recovered string to the original virt.exe.

printf '%s\n' 'gctf{I_h4t3_d3lph1_4nd_n0w_h0pefully_u2}' | ./virt.exe

[+] Access granted. The key you entered is the flag.

Final Flag

gctf{I_h4t3_d3lph1_4nd_n0w_h0pefully_u2}

Summary

  • The success message is shared by two checks. The 39-byte check decodes to wrong{...}.
  • The 40-byte check compares one character at a time. Each match determines the state needed for the next character, and the resulting key passes in the original program.

문제에서 출발하기

유효한 라이선스 키를 찾는 문제다. virt.tar.gz를 풀면 다음과 같은 디렉터리가 생긴다.

virt/
├── virt.exe
└── sha256sum

sha256sum에는 virt.exe의 배포 해시가 적혀 있다. 먼저 virt 디렉터리에서 실행 파일의 형식을 확인했다.

file ./virt.exe

./virt.exe: PE32+ executable for MS Windows 4.00 (console), x86-64 (stripped to external PDB), 8 sections

64비트 Windows 콘솔 프로그램이다. 실행한 뒤 대회 플래그 형식에 맞춰 시험용 키를 넣었다.

./virt.exe

=====================================
   Frostgate License Manager  v3.1
=====================================
Enter license key: gctf{AAAAAAAA}
Checking license, please wait...

[-] Access denied.

시험용 키를 넣자 [-] Access denied.가 나왔다. 성공할 때도 비슷한 문구를 출력한다면, 그 문구를 출력하는 곳에서 거꾸로 검사 조건을 찾을 수 있다. 방금 본 메시지에서 ] Access 부분을 검색했다.

strings -a ./virt.exe | grep -F '] Access '

[+] Access granted. The key you entered is the flag.
[-] Access denied.

성공 메시지에 따르면 검사를 통과한 키 자체가 플래그다.

1. 성공 메시지에서 검사 코드 찾기

실행 파일에서 문자열 상수가 들어 있는 .rdata를 열어 성공 문구의 위치를 찾았다.

objdump -s -j .rdata ./virt.exe | grep -F -A 3 '[+] Access'

10001b360 350a5b2b 5d204163 63657373 20677261  5.[+] Access gra
10001b370 6e746564 2e205468 65206b65 7920796f  nted. The key yo
10001b380 7520656e 74657265 64206973 20746865  u entered is the
10001b390 20666c61 672e0000 130a5b2d 5d204163   flag.....[-] Ac

0x10001b360은 메시지 데이터의 시작 주소다. 0x35는 길이, 0x0a는 줄바꿈이고, 실제 [+] 글자는 두 바이트 뒤에서 시작한다. 코드에서 메시지 데이터의 시작 주소를 사용하는 곳을 찾았다.

objdump -d -M intel --no-show-raw-insn ./virt.exe > virt.asm
grep -F '0x10001b360' virt.asm

100012551: lea r8,[rip+0x8e08]  # 0x10001b360
10001264e: lea r8,[rip+0x8d0b]  # 0x10001b360

두 명령이 같은 성공 문구 주소를 가져온다. 각각 어떤 검사를 거쳐 이곳에 도달하는지 보려고 주변 코드를 펼쳤다. 아래 주소는 방금 찾은 두 참조 위치다.

grep -B 55 -A 30 '100012551:' virt.asm
grep -B 40 -A 30 '10001264e:' virt.asm

두 출력에서 판단에 필요한 줄은 다음과 같다.

10001248c: ret
1000124a4: cmp DWORD PTR [rip+0x13c65],0x28  # 0x100026110
100012533: cmp DWORD PTR [rbp-0x10],0x0
100012551: lea r8,[rip+0x8e08]  # 0x10001b360
1000125b0: ret
1000125d4: cmp DWORD PTR [rip+0x13b35],0x27  # 0x100026110
10001263e: cmp DWORD PTR [rbp-0x8],0x0
10001264e: lea r8,[rip+0x8d0b]  # 0x10001b360
1000126ad: ret

앞 함수의 ret 다음 첫 번째 검사는 0x100026110에 저장된 입력 길이를 0x28(40)과 비교하고, 누적 검사 결과를 확인한 뒤 성공 문구를 사용할 수 있다. 자체 ret 이후의 검사는 같은 길이를 0x27(39)과 비교하며 그 성공 문구를 참조한다. 먼저 39바이트 쪽을 읽었다.

2. 39바이트 검사가 통과시키는 문자열

39바이트 검사에서 성공 문구를 참조하는 줄 위쪽을 펼쳐 비교 반복문을 읽었다.

grep -B 50 '10001264e:' virt.asm

출력에서 관련 줄을 옮기면 다음과 같다.

1000125fd: imul eax,eax,0x2f
100012600: lea eax,[eax+0xa7]
100012612: lea rdx,[rip+0x7277]  # 0x100019890
100012619: movzx ecx,BYTE PTR [rdx+rax*1]
10001261d: xor ecx,DWORD PTR [rbp-0xc]
100012623: lea rax,[rip+0x13aa6]  # 0x1000260d0
10001262a: movzx eax,BYTE PTR [rax+rdx*1]
10001262e: xor ecx,eax
100012630: or ecx,DWORD PTR [rbp-0x8]

이 검사는 입력 39글자를 차례로 확인한다. 위치 i마다 검사 코드에 들어 있는 상수 0x2f(47)와 0xa7(167)을 사용해 (47 * i + 167) & 0xff를 계산한다. 계산값을 0x100019890부터 시작하는 표의 i번째 바이트와 XOR한 뒤, 입력의 i번째 글자와 비교한다. 하나라도 다르면 실패로 기록한다. 따라서 각 위치에서 통과하는 글자는 table[i] ^ ((47 * i + 167) & 0xff)이고, 39글자 모두 복원하려면 표의 내용이 필요하다.

objdump -s ./virt.exe | grep -F -A 2 '100019890'

 100019890 d0a46a5a 04e9a7c1 717a119d a1394b37  ..jZ....qz...9K7
 1000198a0 f3f59614 2adddfd0 7b6119f4 f8a55b6b  ....*...{a....[k
 1000198b0 b3daba24 2d41dc00 00000000 00000000  ...$-A..........

이 세 줄에는 검사에 쓰이는 표의 39바이트가 들어 있다. 각 바이트에 해당 위치의 계산값을 XOR했다.

# decode_decoy.py — written for this write-up
table = bytes.fromhex(
    "d0a46a5a04e9a7c1717a119da1394b37"
    "f3f596142adddfd07b6119f4f8a55b6b"
    "b3daba242d41dc"
)
print(bytes(value ^ ((47 * i + 167) & 0xff)
            for i, value in enumerate(table)).decode())

wrong{f1n4l1z3r_d3c0y_n0t_th3_r34l_0n3}

문자열 자체에 d3c0y라고 적혀 있고 접두어도 대회 형식인 gctf{와 다르다. 같은 성공 문구를 쓰던 40바이트 검사로 돌아갔다.

3. 40바이트 검사에서 한 글자씩 복원하기

다른 성공 문구 참조는 0x100012551에 있었다. 그 위쪽 코드를 읽어 반복문을 확인했다.

grep -B 65 '100012551:' virt.asm

출력에서 관련 줄을 옮기면 다음과 같다.

1000124a4: cmp DWORD PTR [rip+0x13c65],0x28  # 0x100026110
1000124be: xor eax,0xdeadbeef
1000124ef: call 0x100012340
1000124f4: mov DWORD PTR [rbp-0xc],eax
1000124fa: lea rdx,[rip+0x735f]  # 0x100019860
100012501: movzx eax,BYTE PTR [rdx+rax*1]
100012505: xor eax,DWORD PTR [rbp-0xc]
100012508: or eax,DWORD PTR [rbp-0x10]
100012523: call 0x100012410
100012528: mov DWORD PTR [rbp-0x8],eax

한 글자마다 첫 번째 함수에 입력 글자와 현재 상태값, 위치를 넘긴다. 반환값은 표(0x100019860)의 해당 바이트와 비교한다. 두 번째 함수는 그 글자를 반영해 다음 위치에서 쓸 상태값을 만든다.

한 글자라도 다르면 XOR 결과에 1인 비트가 생기고, or로 누적하므로 뒤에서 일치해도 그 비트가 남는다. 결국 모든 위치가 각각 일치해야 한다. 반복문에 들어가기 전에 상태값을 입력 길이 ^ 0xdeadbeef로 초기화하므로 첫 글자를 시험할 때 필요한 값은 이미 안다. 일치하는 글자를 찾을 때마다 두 번째 함수로 상태값을 갱신하면 다음 글자도 같은 방식으로 찾을 수 있다.

두 함수의 내부 계산은 .frost0의 가상 머신이 처리한다. 필요한 건 각 후보를 넣었을 때의 반환값이므로 GDB에서 실행 파일의 두 함수를 직접 호출했다. 디버거에서도 이 반복문에 들어갈 수 있도록 분석용 복사본에서 검사 함수를 선택하는 부분만 바꿨다. 40바이트 시험 입력을 넣고 위 반복문의 첫 call에서 멈춘 뒤, 다음 코드로 출력 가능한 ASCII 문자를 차례로 시험했다.

# recover.gdb — written for this write-up (Python excerpt)
import gdb
target = bytes(gdb.selected_inferior().read_memory(0x100019860, 40))
state = 0xDEADBEC7
flag = bytearray()
for i, want in enumerate(target):
    matches = []
    for ch in range(32, 127):
        result = int(gdb.parse_and_eval(
            "((unsigned int (*)(unsigned int,unsigned int,unsigned int))"
            "0x100012340)(%d,%d,%d)" % (ch, state, i)
        )) & 0xFF
        if result == want:
            matches.append(ch)
    if len(matches) != 1:
        raise RuntimeError("position %d has candidates %r" % (i, matches))
    ch = matches[0]
    flag.append(ch)
    state = int(gdb.parse_and_eval(
        "((unsigned int (*)(unsigned int,unsigned int,unsigned int))"
        "0x100012410)(%d,%d,%d)" % (state, ch, i)
    )) & 0xFFFFFFFF
print("FLAG " + flag.decode("ascii"))

FLAG gctf{I_h4t3_d3lph1_4nd_n0w_h0pefully_u2}

첫 위치에서 표의 첫 바이트 0x2e를 만들어 내는 후보는 g 하나였다. 나머지 위치에서도 한 글자씩만 남았다.

4. 원본에서 키 확인하기

복원한 문자열을 원본 virt.exe에 넣었다.

printf '%s\n' 'gctf{I_h4t3_d3lph1_4nd_n0w_h0pefully_u2}' | ./virt.exe

요약

  • 같은 성공 문구를 출력하는 검사 두 개 중 39바이트 쪽에서 나온 문자열은 wrong{...}였다.
  • 40바이트 쪽에서는 현재 글자가 맞으면 다음 글자를 시험할 상태값도 구할 수 있었다. 이렇게 찾은 키를 원본이 받아들였다.
