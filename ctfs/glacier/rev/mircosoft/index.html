Write Up

Starting from the Challenge

The challenge was tested on Windows 11 Version 10.0.26100. Extracting mircosoft.tar.gz gives four files.

mircosoft/
├── admin_machine.dmp
├── license.bin
├── mircosoft.exe
└── sha256sum

mircosoft.exe is the license validator, license.bin is the license it reads, and admin_machine.dmp is a memory dump from the administrator's machine. The hashes in sha256sum matched the distributed files.

I first checked their formats.

file ./mircosoft.exe ./admin_machine.dmp ./license.bin

./mircosoft.exe:     PE32+ executable for MS Windows 6.00 (console), x86-64, 5 sections
./admin_machine.dmp: Mini DuMP crash report, 5 streams, Thu Jan  1 00:00:00 1970, 0 type
./license.bin:       data

Running the validator with the supplied license produced one useful clue.

./mircosoft.exe

License not valid for this hardware.

The message points to a hardware mismatch. The supplied administrator memory dump is the next clue: it may contain the values from the machine that this license expects.

1. Unpacking the Real Validator

The file format tells us this is a Windows program. I checked its import information to find the file-reading and hardware-checking calls.

objdump -p ./mircosoft.exe | grep -E 'Import Directory|Import Address Table'

Entry 1 0000000000000000 00000000 Import Directory [parts of .idata]
Entry b 0000000000000000 00000000 Bound Import Directory
Entry c 0000000000000000 00000000 Import Address Table Directory
Entry d 0000000000000000 00000000 Delay Import Directory

The import entries are empty. I saved the disassembly and searched it for indirect calls to see where execution passes to code prepared at runtime.

objdump -d -M intel --no-show-raw-insn ./mircosoft.exe > outer.asm
grep -B 5 -A 1 'call   r8' outer.asm

The relevant part of the output is:

14000224b: mov r8,QWORD PTR [rbp-0x51]
14000224f: movabs rdx,0xcafe133700005a42
140002259: add r8,rax
14000225c: call r8

The call passes execution to code prepared in memory. I stopped immediately before it and copied the readable pages starting at that code's base address. The breakpoint offset 0x225c comes from the disassembly above.

# unpack9.gdb — analysis script (excerpt)
set pagination off

import gdb

python
base = int(gdb.parse_and_eval("*(unsigned long long*)($rbp-0x51)"))

for i in range(32):
    try: pages.append(bytes(gdb.selected_inferior().read_memory(base+4096*i,4096)))
    except Exception: break
open("inner-memory.bin", "wb").write(b"".join(pages))
end

I checked the size of the captured file.

wc -c inner-memory.bin

53248 inner-memory.bin

I labeled the dump offsets from 0x140000000 in the disassembly; for example, 0x1400023c6 below corresponds to dump offset 0x23c6.

objdump -D -b binary -m i386:x86-64 -M intel --no-show-raw-insn \
  --adjust-vma=0x140000000 inner-memory.bin > inner.asm

2. Understanding the License Check

The supplied license may give us a recognizable value to search for in the validator. I checked its size and first bytes.

wc -c ./license.bin
xxd -g 1 -l 32 ./license.bin

104 ./license.bin
00000000: 4d 53 4c 43 01 00 00 00 83 05 d5 d5 c5 31 6f 76  MSLC.........1ov
00000010: bd 27 dd bb c5 22 1f 56 ed 81 55 33 e4 68 08 6f  .'...".V..U3.h.o

The file starts with MSLC and a 32-bit version value of 1. I searched the disassembly for the four-byte MSLC value in little-endian order (0x434c534d) and read the surrounding code.

grep -B 45 -A 16 '0x434c534d' inner.asm

The relevant lines of that output are:

140002359: mov r8d,0x68
14000235f: call QWORD PTR [rip+0x2ccb]  # 0x140005030
1400023c6: cmp DWORD PTR [rbp-0x30],0x434c534d
1400023d9: cmp DWORD PTR [rbp-0x2c],0x1
1400023e8: lea r9,[rip+0x3c41]  # 0x140006030
1400023f4: lea r8,[rip+0x3c25]  # 0x140006020
1400023fb: call 0x140001df0

The validator reads the file's 104 bytes, checks the header and version, then calculates a hardware fingerprint using data at 0x140006020 and 0x140006030. Following the later license accesses gives this layout:

Offset Size Meaning
0x00 8 MSLC header and version
0x08 16 hardware fingerprint
0x18 8 nonce
0x20 64 encrypted payload
0x60 8 integrity tag

The fingerprint needs hardware information. I first looked for readable identifiers in the administrator dump.

strings -a admin_machine.dmp | grep -A 1 'ProcessorBrand:'
strings -a admin_machine.dmp | grep -E '[0-9a-f]{8}-([0-9a-f]{4}-){3}[0-9a-f]{12}'

ProcessorBrand:
Intel(R) Core(TM) Ultra 7 155H
658c05ff-e49e-40aa-b041-9a5f56886dea

The dump contains a CPU brand and a MachineGuid. The hardware-collection routine also uses a volume serial, SMBIOS Type 1 UUID, and MAC address. The volume label and network-adapter name help locate the two binary records.

strings -el -t x admin_machine.dmp | grep -F 'Windows'
strings -a -t x admin_machine.dmp | grep -F 'Ethernet'
xxd -g 1 -s 0x9200 -l 32 admin_machine.dmp
xxd -g 1 -s 0x72c8 -l 160 admin_machine.dmp

The relevant lines are:

   920a Windows
   72c8 Intel(R) Ethernet Controller I225-V
00009200: 91 4c 8d d4 0e 00 00 00 00 00 57 00 69 00 6e 00  .L........W.i.n.
00009210: 64 00 6f 00 77 00 73 00 00 00 00 00 00 00 00 00  d.o.w.s.........
000072c8: 49 6e 74 65 6c 28 52 29 20 45 74 68 65 72 6e 65  Intel(R) Etherne
00007348: 00 00 00 00 06 00 00 00 52 54 00 36 e6 64 00 00  ........RT.6.d..
00007358: 01 00 00 00 06 00 00 00 01 00 00 00 00 00 00 00  ................

The volume record places its four-byte serial at 0x9200, just before the Windows label. The adapter record contains a six-byte address at 0x7350. The SMBIOS Type 1 record begins with type 01 and length 1b; its UUID starts eight bytes into that record. The collection routine joins CPU (48 bytes), volume serial (4), MachineGuid (36), UUID (16), and MAC (6) into a 110-byte buffer. I extracted those fields as follows.

# solve.py — written for this write-up (excerpt)
from pathlib import Path
import re
import struct

dump = Path("admin_machine.dmp").read_bytes()
license_data = Path("license.bin").read_bytes()

cpu = dump[dump.index(b"ProcessorBrand:") + 16:][:48]
volume_serial = dump[0x9200:0x9204]
machine_guid = re.search(
    rb"[0-9a-f]{8}-(?:[0-9a-f]{4}-){3}[0-9a-f]{12}", dump
).group()
smbios_type1 = dump.index(b"\x01\x1b")
system_uuid = dump[smbios_type1 + 8:smbios_type1 + 24]
mac = dump[0x7350:0x7356]

hardware = cpu + volume_serial + machine_guid + system_uuid + mac
assert len(hardware) == 110

CPU:          Intel(R) Core(TM) Ultra 7 155H
Volume:       914c8dd4
MachineGuid:  658c05ff-e49e-40aa-b041-9a5f56886dea
System UUID:  3c31a857b2b700488ce185385968c8a8
MAC:          52540036e664

The recovered fields have the expected sizes and concatenate to 110 bytes. The fingerprint comparison below checks their contents and order.

3. Recreating the Fingerprint and Key

The fingerprint call above refers to data at 0x140006020 and 0x140006030. In a mapped image, those addresses correspond to dump offsets 0x6020 and 0x6030. I first checked the GDB dump.

xxd -p -s 0x6000 -l 16 inner-memory.bin

cc97f65875384078697972e1bc1c947b

The first debugger capture has different table bytes. A later capture of the normal check, saved as inner-clean-runtime.bin, contains the values used for the fingerprint and key. I read the four adjacent 16-byte tables from that capture.

xxd -g 1 -s 0x6000 -l 64 inner-clean-runtime.bin

00006000: 67 e6 09 6a 85 ae 67 bb 72 f3 6e 3c 3a f5 4f a5
00006010: 7f 52 0e 51 8c 68 05 9b ab d9 83 1f 19 cd e0 5b
00006020: 98 2f 8a 42 91 44 37 71 cf fb c0 b5 a5 db b5 e9
00006030: 5b c2 56 39 f1 11 f1 59 a4 82 3f 92 d5 5e 1c ab

The last two tables correspond to the two addresses in the fingerprint call. The first two are used by the license-key path. I translated the inner program's 32-round TEA-like update function into tea and update helpers. The excerpt below shows how the hardware and the four tables are passed to those helpers.

# solve.py — written for this write-up (core excerpt)
TABLES = Path("inner-clean-runtime.bin").read_bytes()[0x6000:0x6040]
MASK = 0xffffffff

fingerprint = struct.pack("<4I", *update(
    (0x67452301, 0xefcdab89, 0x98badcfe, 0x10325476),
    hardware, TABLES[32:48], TABLES[48:64],
))
assert fingerprint == license_data[8:24]

state = (0, 0, 0, 0)
for part in (cpu, volume_serial + machine_guid, system_uuid + mac):
    state = update(state, part, TABLES[:16], TABLES[16:32])

a, b, c, d = state
rol7 = lambda value: ((value << 7) | (value >> 25)) & MASK
a = ((rol7(a) ^ b) + c) & MASK
b = ((rol7(b) ^ c) + d) & MASK
c = ((rol7(c) ^ d) + a) & MASK
d = ((rol7(d) ^ a) + b) & MASK
key = struct.pack("<4I", a, b, c, d)

The full 110-byte hardware buffer produces the fingerprint stored in license.bin[8:24]. That exact match confirms the recovered values and their order. The key path processes the hardware in three groups—CPU, volume plus MachineGuid, and UUID plus MAC—and applies the final mixing step shown above. The resulting key is 3b8652afcde7de87294a383867f1a9f7.

4. Verifying and Decrypting the License

I used the recovered key to check the integrity tag and decrypt the payload.

# solve.py — written for this write-up (continued)
x = y = 0
for offset in range(0, 96, 8):
    p, q = struct.unpack_from("<2I", license_data, offset)
    x, y = tea(x ^ p, y ^ q, key)
x, y = tea(x, y, key)
assert struct.pack("<2I", x, y) == license_data[96:104]

nonce0, nonce1 = struct.unpack_from("<2I", license_data, 24)
plain = bytearray()
for counter in range(8):
    stream = struct.pack(
        "<2I", *tea((nonce0 + counter) & MASK, nonce1, key)
    )
    block = license_data[32 + counter * 8:40 + counter * 8]
    plain.extend(left ^ right for left, right in zip(block, stream))

flag = plain.rstrip(b"\0").decode()
print("fingerprint:", fingerprint.hex())
print("key:", key.hex())
print("flag:", flag)

fingerprint: 8305d5d5c5316f76bd27ddbbc5221f56
key: 3b8652afcde7de87294a383867f1a9f7
flag: gctf{m3m0ry_dump_DRM_c3rt_f0rg3d_7b2e}

The fingerprint matches the 16 bytes stored in the license, and the calculated integrity tag matches its final eight bytes. The 64-byte payload then decrypts to the flag shown above. The original program rejects the current PC because its hardware differs from the administrator's.

Final Flag

gctf{m3m0ry_dump_DRM_c3rt_f0rg3d_7b2e}

Summary

  • The visible executable prepared the license-checking code in memory and transferred execution to it.
  • The administrator's memory dump contained the five hardware values bound to license.bin.
  • Recreating the stored fingerprint confirmed the extracted values. The resulting key also produced the correct integrity tag before decrypting the flag.
TACTICAL FLOW MAP
  1. Run the supplied validator
  2. Unpack the inner license checker
  3. Recover the registered hardware from the memory dump
  4. Recreate the fingerprint and encryption key
  5. Verify the integrity tag
  6. Decrypt the license payload

문제에서 출발하기

Windows 11 Version 10.0.26100에서 테스트된 문제다. mircosoft.tar.gz를 풀면 파일 네 개가 나온다.

mircosoft/
├── admin_machine.dmp
├── license.bin
├── mircosoft.exe
└── sha256sum

mircosoft.exe는 라이선스 검사 프로그램, license.bin은 프로그램이 읽는 라이선스, admin_machine.dmp는 관리자의 PC에서 가져온 메모리 덤프다. sha256sum에 적힌 해시는 배포된 파일과 일치했다.

먼저 각 파일의 형식을 확인했다.

file ./mircosoft.exe ./admin_machine.dmp ./license.bin

./mircosoft.exe:     PE32+ executable for MS Windows 6.00 (console), x86-64, 5 sections
./admin_machine.dmp: Mini DuMP crash report, 5 streams, Thu Jan  1 00:00:00 1970, 0 type
./license.bin:       data

제공된 라이선스와 함께 프로그램을 실행하자 단서가 하나 나왔다.

./mircosoft.exe

License not valid for this hardware.

출력은 현재 PC의 하드웨어가 라이선스와 맞지 않는다고 알려 준다. 함께 제공된 관리자 메모리 덤프에서 라이선스가 요구하는 PC의 값을 찾을 수 있는지 살펴봤다.

1. 실제 검증 코드 꺼내기

파일 형식에서 Windows 프로그램임을 확인했다. 파일 읽기와 하드웨어 검사 함수를 찾기 위해 임포트 정보를 확인했다.

objdump -p ./mircosoft.exe | grep -E 'Import Directory|Import Address Table'

Entry b 0000000000000000 00000000 Bound Import Directory
Entry c 0000000000000000 00000000 Import Address Table Directory
Entry d 0000000000000000 00000000 Delay Import Directory

임포트 항목이 비어 있다. 실행 중 준비된 코드로 넘어가는 지점을 찾기 위해 디스어셈블 결과를 저장하고 간접 호출의 주변을 살폈다.

objdump -d -M intel --no-show-raw-insn ./mircosoft.exe > outer.asm
grep -B 5 -A 1 'call   r8' outer.asm

출력 중 관련 부분은 다음과 같다.

제공된 라이선스 파일에서 검증 코드를 찾을 만한 값을 먼저 확인했다. 파일의 길이와 첫 바이트를 살폈다.

3. 하드웨어 지문과 키 다시 만들기

앞서 본 지문 계산 호출은 0x140006020과 0x140006030의 데이터를 참조한다. 메모리에 배치한 이미지에서 이 주소들은 덤프 파일의 0x6020과 0x6030 오프셋이다. 먼저 GDB 덤프의 값을 살폈다.

xxd -p -s 0x6000 -l 16 inner-memory.bin

cc97f65875384078697972e1bc1c947b

첫 디버거 캡처와 정상 검사 때의 표 바이트는 다르다. 분석 중 정상 검사 경로에서 캡처한 inner-clean-runtime.bin에서 지문과 키 계산에 쓰인 값을 확인했다. 연속된 16바이트 표 네 개를 읽었다.

xxd -g 1 -s 0x6000 -l 64 inner-clean-runtime.bin

뒤쪽 표 두 개는 앞서 본 지문 계산 호출에 연결된다. 앞쪽 두 개는 라이선스 키를 만드는 경로에서 사용한다. 내부 프로그램의 32라운드 TEA 계열 상태 갱신 함수를 tea와 update로 옮겼다. 아래에는 하드웨어 값과 표 네 개를 두 함수에 전달하는 핵심 부분을 남겼다.

# solve.py — written for this write-up (core excerpt)
TABLES = Path("inner-clean-runtime.bin").read_bytes()[0x6000:0x6040]
MASK = 0xffffffff

fingerprint = struct.pack("<4I", *update(
    (0x67452301, 0xefcdab89, 0x98badcfe, 0x10325476),
    hardware, TABLES[32:48], TABLES[48:64],
))
assert fingerprint == license_data[8:24]

state = (0, 0, 0, 0)
for part in (cpu, volume_serial + machine_guid, system_uuid + mac):
    state = update(state, part, TABLES[:16], TABLES[16:32])

a, b, c, d = state
rol7 = lambda value: ((value << 7) | (value >> 25)) & MASK
a = ((rol7(a) ^ b) + c) & MASK
b = ((rol7(b) ^ c) + d) & MASK
c = ((rol7(c) ^ d) + a) & MASK
d = ((rol7(d) ^ a) + b) & MASK
key = struct.pack("<4I", a, b, c, d)

110바이트 하드웨어 전체로 계산한 지문은 license.bin[8:24]와 일치했다. 이 일치로 덤프에서 복원한 값과 결합 순서를 확인했다. 키 생성 경로는 CPU, 볼륨 시리얼과 MachineGuid, UUID와 MAC의 세 묶음을 차례로 처리하고 마지막 혼합 연산을 적용한다. 그 결과 키는 3b8652afcde7de87294a383867f1a9f7이다.

4. 라이선스 검증하고 복호화하기

복원한 키로 무결성 태그를 확인하고 암호화된 데이터를 복호화했다.

# solve.py — written for this write-up (continued)
x = y = 0
for offset in range(0, 96, 8):
    p, q = struct.unpack_from("<2I", license_data, offset)
    x, y = tea(x ^ p, y ^ q, key)
x, y = tea(x, y, key)
assert struct.pack("<2I", x, y) == license_data[96:104]

nonce0, nonce1 = struct.unpack_from("<2I", license_data, 24)
plain = bytearray()
for counter in range(8):
    stream = struct.pack(
        "<2I", *tea((nonce0 + counter) & MASK, nonce1, key)
    )
    block = license_data[32 + counter * 8:40 + counter * 8]
    plain.extend(left ^ right for left, right in zip(block, stream))

flag = plain.rstrip(b"\0").decode()
print("fingerprint:", fingerprint.hex())
print("key:", key.hex())
print("flag:", flag)
