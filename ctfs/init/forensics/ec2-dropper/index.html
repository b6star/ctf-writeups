ec2-dropper

AUTHOR Kshitij Raj

An EC2 instance in our web tier was found running an unauthorised scheduled script, /opt/agent/vault.py, installed right after an SSH login from an address nobody recognised. The script keeps its configuration in an encrypted vault — and the key isn't stored on disk. It's derived at runtime from the instance's own identity.

We pulled the script, the vault, and the host logs. Review the code, work out how the vault is keyed, and recover the operator's configuration note.

웹 계층의 EC2 인스턴스에서 허가받지 않은 예약 스크립트 `/opt/agent/vault.py`가 실행되고 있었다. 이 스크립트는 아무도 모르는 주소에서 SSH로 로그인한 직후 설치됐다. 설정은 암호화된 vault에 보관하고, 키는 디스크에 저장하지 않고 인스턴스의 고유 정보에서 실행 중에 만든다.

스크립트와 vault, 호스트 로그를 확보했다. 코드를 읽고 vault 키가 만들어지는 방식을 알아내 운영자의 설정 메모를 복구하라.

Write Up

Starting from the Challenge

The incident archive contains INCIDENT.txt, vault.py, vault.bin, and cloud-init logs. I opened vault.py first to see how it derives the key for vault.bin.

1. Rebuilding the key from the instance identity

vault.py contains this key-derivation function:

# vault.py — challenge file (excerpt)
SALT = "s4lt_"

def derive_key(iid: str) -> bytes:
    return hashlib.sha256((SALT + iid).encode()).digest()

It prepends s4lt_ to the EC2(Elastic Compute Cloud) instance ID and uses the 32-byte SHA-256 result as the AES key.

Q: Where can the same instance ID be recovered from the incident files?

Cloud-init records information about the instance initialization process, so I opened cloud-init-output.log.

instance-id: i-0a1b2c3d4e5f67890

2. Splitting the IV and ciphertext

The encryption code stores the 16-byte IV(Initialization Vector) at the beginning of vault.bin, followed by the AES-CBC ciphertext. CBC requires both the correct key and the IV used to process the first block. I split the file at that boundary.

# solve.py — written for this write-up
import hashlib
import json
from pathlib import Path
from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad

instance_id = "i-0a1b2c3d4e5f67890"
key = hashlib.sha256(("s4lt_" + instance_id).encode()).digest()

blob = Path("vault.bin").read_bytes()
iv, ciphertext = blob[:16], blob[16:]
plain = unpad(AES.new(key, AES.MODE_CBC, iv).decrypt(ciphertext), 16)

data = json.loads(plain)
print(data["operator_note"])

The code recalculates the key from the instance ID, decrypts the CBC ciphertext, and removes the PKCS#7 padding. It then parses the plaintext as JSON and prints operator_note. I also checked the padding and JSON structure of the decrypted result.

3. Reading the operator note

The Flag was in operator_note inside the recovered JSON. Both inputs to the hash were available in the archive, so the AES key could be reproduced exactly.

  • Vault: Split the prepended IV, decrypt the CBC data, and read operator_note from the JSON.

문제에서 출발하기

사건 압축 파일에는 INCIDENT.txt, vault.py, vault.bin과 cloud-init 로그가 있다. 먼저 vault.py를 열어 vault.bin의 키를 만드는 방식을 확인했다.

1. 인스턴스 정보에서 키 다시 만들기

vault.py에는 다음 키 생성 함수가 있다.

# vault.py — challenge file (excerpt)
SALT = "s4lt_"

def derive_key(iid: str) -> bytes:
    return hashlib.sha256((SALT + iid).encode()).digest()

EC2(Elastic Compute Cloud) instance ID 앞에 s4lt_를 붙이고, SHA-256 결과 32바이트를 AES 키로 사용한다.

Q: 사건 파일 안에서 같은 instance ID를 어디서 찾을 수 있을까?

cloud-init은 인스턴스 초기화 과정을 로그에 남기므로 cloud-init-output.log를 열었다.

instance-id: i-0a1b2c3d4e5f67890

2. IV와 암호문 분리하기

암호화 코드는 vault.bin 앞 16바이트를 IV(Initialization Vector)로 두고 그 뒤에 AES-CBC 암호문을 붙인다. CBC에서는 올바른 키뿐 아니라 첫 블록 처리에 쓰이는 IV도 필요하다. 파일을 이 경계에 맞춰 나눈다.

# solve.py — written for this write-up
import hashlib
import json
from pathlib import Path
from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad

instance_id = "i-0a1b2c3d4e5f67890"
key = hashlib.sha256(("s4lt_" + instance_id).encode()).digest()

blob = Path("vault.bin").read_bytes()
iv, ciphertext = blob[:16], blob[16:]
plain = unpad(AES.new(key, AES.MODE_CBC, iv).decrypt(ciphertext), 16)

data = json.loads(plain)
print(data["operator_note"])

코드는 instance ID에서 키를 다시 계산하고, CBC 복호화 뒤 PKCS#7 패딩을 제거한다. 이어 JSON으로 파싱해 operator_note를 출력한다. 복호화 결과의 패딩과 JSON 구조도 확인했다.

3. operator_note 확인하기

복원된 JSON의 operator_note에 Flag가 있었다. 파일과 키 파생 코드, 인스턴스 로그를 연결하면 비밀처럼 보이던 키를 재생성할 수 있었다. instance ID와 고정 문자열이 모두 공개되어 있어 같은 키를 그대로 만들 수 있었다.
