leaky history

AUTHOR Kshitij Raj

A developer on the Tanvoro deploy team realised they'd committed a secrets file to the tanvoro-deploy repo. In a panic they "cleaned it up" — dropped the commit, scrubbed their tracks. The repo looks spotless now: git log shows nothing out of place.

We recovered a copy of the repository. The secret isn't in the history anymore... but git rarely throws anything away. Get it back.

Tanvoro 배포 팀의 개발자가 `tanvoro-deploy` 저장소에 비밀 파일을 커밋했다는 사실을 알아챘다. 당황한 개발자는 커밋을 기록에서 없애고 흔적을 지웠다. 지금 저장소의 `git log`는 아무 문제도 없어 보인다.

저장소 사본을 확보했다. 비밀은 더 이상 기록에 없지만 Git은 좀처럼 데이터를 버리지 않는다. 그것을 복구하라.

Write Up

Starting from the Challenge

The deleted deployment secret must be recovered from the provided Git repository. The current files no longer contain it, so I examined the repository's earlier objects. Git stores commits, directory structures, and file contents separately, which can leave a deleted file recoverable until garbage collection removes its objects.

1. Looking beyond git log

git log --oneline --decorate --all --graph
git reflog show --all
git show --stat ORIG_HEAD

The current history showed four normal commits, and the reflog was empty. ORIG_HEAD still pointed to a commit that was unreachable from the current branch. ORIG_HEAD is a reference that preserves HEAD from before certain Git operations.

Q: Could the discarded commit still be found if that reference were missing?

I inspected every unreachable object.

git fsck --full --unreachable --no-reflogs

--unreachable displays objects that cannot be reached from current references, while --no-reflogs excludes reflogs when determining reachability. This revealed commit, tree, and blob objects. It confirmed that cleaning up history does not remove the contents unless garbage collection actually deletes the objects.

2. Recovering the path and blob

git ls-tree -r 6dfa863c4a9a1700c6f09a608761f82ef9c241a2
git cat-file -p 4d080a754db9fdfdeeefb7c4da53dd2b4b11206a

ls-tree -r traverses the commit's directory tree and associates paths with object IDs. The relevant blob was deploy/secrets.env. I then used cat-file -p to read the blob's original bytes.

DEPLOY_TOKEN=InIt{d4ngl1ng_c0mm1t_l34k}

3. Finding the same object without ORIG_HEAD

# solve.py — written for this write-up (excerpt)
fsck = git("fsck", "--full", "--unreachable", "--no-reflogs")
commits = re.findall(rb"unreachable commit ([0-9a-f]{40})", fsck)

for commit in commits:
    for entry in git("ls-tree", "-rz", commit.decode()).split(b"\0"):
        if not entry:
            continue
        metadata, path = entry.split(b"\t", 1)
        _, kind, object_id = metadata.split()
        if kind == b"blob":
            content = git("cat-file", "blob", object_id.decode())
            for flag in re.findall(rb"InIt\{[^{}]+\}", content):
                print(path.decode(), flag.decode())

The script examines the trees and blobs of every commit found by git fsck. It recovered the same file and string without directly specifying ORIG_HEAD. The value calculated from the recovered bytes with git hash-object --stdin also matched the original blob ID, confirming that both the filename and contents were identical.

Final Flag

Summary

  • Clue: ORIG_HEAD still points to the discarded commit.
  • Object search: git fsck also finds the unreachable commit, tree, and blob.
  • Recovery: The commit tree maps deploy/secrets.env to the blob containing the deployment token.

문제에서 출발하기

제공된 Git 저장소에서 삭제된 배포 비밀을 찾아야 한다. 현재 파일에는 남아 있지 않아 이전 객체를 살펴봤다. Git은 커밋·디렉터리 구조·파일 내용을 따로 저장하므로, 브랜치 기록에서 지운 파일도 garbage collection이 객체를 정리하기 전까지 복구할 수 있다.

1. git log 밖의 객체 찾기

git log --oneline --decorate --all --graph
git reflog show --all
git show --stat ORIG_HEAD

현재 기록에는 정상 커밋 네 개가 보였고 reflog는 비어 있었다. ORIG_HEAD는 현재 브랜치에서 도달할 수 없는 커밋을 가리켰다. ORIG_HEAD는 일부 Git 작업 직전의 HEAD를 보관하는 참조다.

Q: 이 참조가 없어도 버려진 커밋을 찾을 수 있을까?

도달할 수 없는 객체를 모두 검사했다.

git fsck --full --unreachable --no-reflogs

--unreachable은 현재 참조에서 도달할 수 없는 객체를 표시하고, --no-reflogs는 reflog를 도달 가능성의 기준에서 제외한다. 여기서 commit, tree, blob이 발견됐다. 기록을 정리해도 garbage collection으로 객체를 실제 제거하지 않으면 내용이 남는다는 것을 확인했다.

2. 파일 경로와 Blob 복구하기

git ls-tree -r 6dfa863c4a9a1700c6f09a608761f82ef9c241a2
git cat-file -p 4d080a754db9fdfdeeefb7c4da53dd2b4b11206a

ls-tree -r는 해당 커밋의 디렉터리를 순회해 경로와 객체 ID를 연결한다. 문제의 Blob은 deploy/secrets.env였다. 이어 cat-file -p로 Blob의 원래 바이트를 읽었다.

DEPLOY_TOKEN=InIt{d4ngl1ng_c0mm1t_l34k}

3. ORIG_HEAD 없이 같은 객체 찾기

# solve.py — written for this write-up (excerpt)
fsck = git("fsck", "--full", "--unreachable", "--no-reflogs")
commits = re.findall(rb"unreachable commit ([0-9a-f]{40})", fsck)

for commit in commits:
    for entry in git("ls-tree", "-rz", commit.decode()).split(b"\0"):
        if not entry:
            continue
        metadata, path = entry.split(b"\t", 1)
        _, kind, object_id = metadata.split()
        if kind == b"blob":
            content = git("cat-file", "blob", object_id.decode())
            for flag in re.findall(rb"InIt\{[^{}]+\}", content):
                print(path.decode(), flag.decode())

작성한 스크립트는 git fsck가 찾은 커밋마다 tree와 blob을 조사한다. ORIG_HEAD를 직접 지정하지 않아도 같은 파일과 문자열이 나왔다. 복구한 바이트를 git hash-object --stdin으로 계산한 값도 원래 Blob ID와 같았다. 파일 이름뿐 아니라 내용까지 동일하다는 검증이다.

요약

  • 단서: ORIG_HEAD가 기록에서 버린 커밋을 가리킨다.
  • 객체 검색: git fsck에서도 도달할 수 없는 commit, tree, blob이 나온다.
  • 복구: 커밋 tree에서 deploy/secrets.env의 Blob을 찾아 배포 토큰을 읽는다.
