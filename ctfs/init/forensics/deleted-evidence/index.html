deleted evidence

AUTHOR Kshitij Raj

It started at 02:14 on a Sunday. Tanvoro Systems' monitoring lit up red — gigabytes of source code and unreleased product designs pouring out of a developer's workstation to an address nobody recognised. By the time the on-call analyst reached the floor and ripped out the network cable, the intruder had been inside for hours — and had spent the last of them calmly deleting files, trying to erase every trace of what they'd touched.

We seized the drive before it could be wiped and imaged it. The suspect is certain the evidence is gone for good. But on a filesystem, Delete doesn't mean erased — it just means forgotten.

Find what they tried to bury.

일요일 새벽 2시 14분, Tanvoro Systems의 모니터링 시스템에 경고가 울렸다. 개발자 워크스테이션에서 정체를 알 수 없는 주소로 수 GB의 소스 코드와 미공개 제품 설계가 빠져나가고 있었다. 당직 분석가가 현장에 도착해 네트워크 케이블을 뽑았을 때, 침입자는 이미 몇 시간 동안 시스템 안에 있었고 마지막에는 흔적을 지우려고 파일을 차분히 삭제하고 있었다.

드라이브가 완전히 지워지기 전에 확보해 이미지를 만들었다. 용의자는 증거가 영원히 사라졌다고 확신하지만, 파일시스템에서 Delete는 삭제된 데이터를 잊었다는 뜻일 뿐이다.

그들이 묻으려 한 것을 찾아라.

Write Up

Starting from the Challenge

The deleted evidence must be recovered from the provided evidence.img. Deletion does not always overwrite a file's contents with zeroes immediately. The starting point is to check whether filesystem metadata and data remain even after the file disappears from its directory.

1. Locating the NTFS partition

mmls evidence.img

Reading the MBR(Master Boot Record) shows that the first partition begins at LBA(Logical Block Addressing) 2048. I confirmed the NTFS signature in that partition's boot sector.

2. Recovering the deleted file by its MFT record

# command
fls -o 2048 -r -d evidence.img

# result
-/r * 75-128-2: Users/j.morris/Documents/recovery_code.gz
-/r * 16:       $OrphanFiles/OrphanFile-16
-/r * 17:       $OrphanFiles/OrphanFile-17
# omitted below

Q: In 75-128-2, which number identifies the file for extraction?

I used The Sleuth Kit's fls -r -d to list deleted entries recursively and found recovery_code.gz in MFT(Master File Table) record 75. This small file used resident storage, meaning its data was stored inside the MFT record, and 46 bytes remained after deletion.

icat -o 2048 evidence.img 75 > recovery_code.gz
file recovery_code.gz
gzip -dc recovery_code.gz

icat extracts the file contents from the specified record. I checked the format with file and decompressed it with gzip -dc. This produced the following value.

VaVg{q3y3g3q_ohg_a0g_t0a3}

3. Why ROT13?

The braces suggest Leet Speak, while the prefix is VaVg. Applying ROT13(Rotation 13), which shifts letters by 13 positions, changes it to InIt, so I applied the same transformation to the entire string.

# decode.py — written for this write-up
import codecs
print(codecs.decode("VaVg{q3y3g3q_ohg_a0g_t0a3}", "rot_13"))

Final Flag

InIt{d3l3t3d_but_n0t_g0n3}

Summary

  • Partition: The NTFS volume starts at sector 2048.
  • Deleted entry: fls identifies recovery_code.gz as MFT record 75.
  • Recovery: Extract the resident Gzip data and apply ROT13 to its contents.
TACTICAL FLOW MAP
  1. evidence.img
  2. NTFS at sector 2048
  3. Deleted MFT record 75
  4. icat → recovery_code.gz
  5. Gzip decompress

문제에서 출발하기

제공된 evidence.img에서 삭제된 증거를 복구해야 한다. 삭제는 파일 내용을 즉시 0으로 덮는 동작과 다를 수 있다. 디렉터리에서 사라져도 파일시스템 메타데이터와 데이터가 남아 있는지를 살펴보는 것이 출발점이다.

1. NTFS 파티션 위치 찾기

mmls evidence.img

MBR(Master Boot Record) 정보를 읽으면 첫 파티션이 LBA(Logical Block Addressing) 2048에서 시작한다. 해당 부트 섹터에서 NTFS 시그니처를 확인했다.

2. MFT 레코드로 삭제 파일 복구하기

# command
fls -o 2048 -r -d evidence.img

# result
-/r * 75-128-2: Users/j.morris/Documents/recovery_code.gz
-/r * 16:       $OrphanFiles/OrphanFile-16
-/r * 17:       $OrphanFiles/OrphanFile-17
# 이후 생략

Q: 75-128-2에서 파일을 추출할 때 사용하는 번호는 무엇일까?

The Sleuth Kit의 fls -r -d로 재귀적으로 삭제 항목을 조회했다. recovery_code.gz와 MFT(Master File Table) record 75를 확인했다. 이 작은 파일은 데이터가 MFT 레코드 안에 저장되는 resident 형태였고, 삭제 이후에도 46바이트 내용이 남아 있었다.

icat -o 2048 evidence.img 75 > recovery_code.gz
file recovery_code.gz
gzip -dc recovery_code.gz

icat은 지정한 레코드의 파일 내용을 추출한다. file로 형식을 확인하고 gzip -dc로 압축을 풀었다. 이때 읽은 결과는 아래와 같다.

VaVg{q3y3g3q_ohg_a0g_t0a3}

3. ROT13을 적용한 이유

복구된 문자열은 중괄호를 포함한 플래그 형태이고 접두부가 VaVg다. 알파벳을 13칸 옮기는 ROT13(Rotation 13)을 적용하면 InIt가 되므로 같은 변환을 전체 문자열에 적용했다.

# decode.py — written for this write-up
import codecs
print(codecs.decode("VaVg{q3y3g3q_ohg_a0g_t0a3}", "rot_13"))

Final Flag

InIt{d3l3t3d_but_n0t_g0n3}

요약

  • 파티션: NTFS 볼륨은 2048번 섹터에서 시작한다.
  • 삭제 항목: fls에서 recovery_code.gz가 MFT 레코드 75로 확인된다.
  • 복구: resident Gzip 데이터를 추출하고 그 내용에 ROT13을 적용한다.
