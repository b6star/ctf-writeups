Red John Returns

AUTHOR Harsh Agarwal

Red John has gone quiet, but his account is still active. Patrick suspects he has left something new for him to find. Look for Red John’s trail again, follow it to his latest work, and see whether you can read what he has written.

Flag format: InIt{...} Lowercase letters, digits and underscores only, with no spaces. If you want to check your answer before submitting, hash the complete flag, including InIt{ and }.

Write Up

Starting from the Challenge

The challenge links to for_patrick on GitHub. It contains ten entries that mix hashes with questions, alongside the sentences 'I never liked even company.' and 'Five of these are mine.' I numbered them from 1 and selected entries 1, 3, 5, 7, and 9.

1. Taking the odd-numbered clues

The first value has the form of an MD5 hash, while the fifth has the form of a SHA-256 hash. I hashed candidate words and compared the results with the given values. Public searches and a local wordlist comparison identified smiley and teacup, respectively.

The answer to the third question is 1988, the year of the Morris worm, and the seventh is 3389, the default RDP(Remote Desktop Protocol) port. Four values were now determined, but the plaintext of the final 32-character hash was still unknown.

2. Rechecking the last 32-character hash

I initially treated the final value, 9d7f37db9e15ce06e8274a36bdd6cce3, as MD5 as well. I checked an English dictionary, roughly 14.34 million lines from RockYou, numeric candidates, combinations of words from the previous article, and public reverse-hash searches, but none matched.

Q: Does a 32-character hexadecimal value have to be MD5?

NTLM(New Technology LAN Manager) also produces a value of that length. Testing candidates with NTLM's UTF-16LE encoding followed by MD4 produced an exact match for lisbon.

3. Verifying the Recovered Words Against the Original Hashes

# verify_hashes.py — written for this write-up
from hashlib import md5, sha256
from Crypto.Hash import MD4

assert md5(b"smiley").hexdigest() == "d1b145842e9b731a66eef0ee6fc33497"
assert sha256(b"teacup").hexdigest() == "417f1824ba04658978262aea110b75724ed39c984ccbed0b5c56a7ad801d0f1c"
assert MD4.new("lisbon".encode("utf-16le")).hexdigest() == "9d7f37db9e15ce06e8274a36bdd6cce3"
print("smiley / 1988 / teacup / 3389 / lisbon")

I calculated the hashes of the recovered words and compared them directly with the given values.

4. Formatting the five recovered values

Following GitHub's instruction 'all in lowercase with nothing in between', I joined the five values in lowercase without separators. The first eight characters of the completed string's SHA-256 were given as 'aa999a60'. init{smiley1988teacup3389lisbon}, using the lowercase prefix, matched this verification value but was rejected when submitted. Versions without separators using the Init and InIt prefixes were also rejected.

The live challenge board already showed solves from other teams, which made it unlikely that the entire challenge was not being scored. I then followed the challenge description, 'Lowercase letters, digits and underscores only, with no spaces.', and submitted the five elements joined by underscores. This was marked Correct.

(The final value's SHA-256 begins with a0a23f8e..., which differs from GitHub's verification prefix. The GitHub verification hint did not match the value used by the scoring system, and the underscore-separated string was the one accepted as correct.)

Final Flag

InIt{smiley_1988_teacup_3389_lisbon}

문제에서 출발하기

문제에 제시된 for_patrick on GitHub을 열었다. 열 개의 항목에 해시와 질문이 섞여 있고 'I never liked even company.', 'Five of these are mine.'이라는 문장이 있다. 따라서 1부터 번호를 세어 1·3·5·7·9번만 골랐다.

1. 홀수 번째 단서 다섯 개 풀기

1번은 MD5, 5번은 SHA-256 형태다. 단어 후보의 해시를 계산해 주어진 값과 비교했다. 공개 검색과 로컬 사전 대조에서 각각 smiley와 teacup을 확인했다.

3번은 Morris worm이 발생한 연도 1988, 7번은 RDP의 기본 포트 3389다. 이 시점에서 네 값은 정해졌지만 마지막 32자리 해시의 원문은 남아 있었다.

2. 마지막 32자리 해시 다시 확인하기

마지막 값 9d7f37db9e15ce06e8274a36bdd6cce3도 처음에는 MD5로 보았다. 영어 사전, RockYou 약 1,434만 줄, 숫자 후보, 이전 글의 단어 조합과 공개 역해시 조회까지 확인했지만 일치하지 않았다.

Q: 32자리 16진수 값은 반드시 MD5일까?

NTLM(New Technology LAN Manager)도 같은 길이의 결과를 사용한다. UTF-16LE 인코딩 후 MD4를 적용하는 NTLM 방식으로 후보를 검사하자 lisbon이 정확히 일치했다.

3. 찾은 단어를 원문 해시와 검산하기

# verify_hashes.py — written for this write-up
from hashlib import md5, sha256
from Crypto.Hash import MD4

assert md5(b"smiley").hexdigest() == "d1b145842e9b731a66eef0ee6fc33497"
assert sha256(b"teacup").hexdigest() == "417f1824ba04658978262aea110b75724ed39c984ccbed0b5c56a7ad801d0f1c"
assert MD4.new("lisbon".encode("utf-16le")).hexdigest() == "9d7f37db9e15ce06e8274a36bdd6cce3"
print("smiley / 1988 / teacup / 3389 / lisbon")

찾은 단어의 해시를 직접 계산해 주어진 값과 대조했다.

4. 다섯 값을 플래그 형식에 맞추기

GitHub의 'all in lowercase with nothing in between'에 따라 다섯 값을 소문자로 구분자 없이 연결했다. 완성 문자열의 SHA-256 앞 8자리는 'aa999a60'으로 제시됐다. 소문자 접두부를 사용한 init{smiley1988teacup3389lisbon}은 이 검증값과 일치했지만 제출에서 거절됐다. 접두부를 Init, InIt로 바꾼 구분자 없는 형태도 모두 거절됐다.

실시간 문제 설명판에는 이미 다른 팀의 solves 정보가 있어 문제 전체가 채점되지 않는다는 가설도 약해졌다. 문제 설명의 'Lowercase letters, digits and underscores only, with no spaces.'에 맞춰 다섯 요소를 밑줄로 연결해 제출하자 Correct가 표시됐다.

(최종값의 SHA-256은 a0a23f8e...로 GitHub의 검증 접두사와 다르다. GitHub 검증 힌트와 실제 채점값이 일치하지 않았고, 정답으로 처리된 것은 밑줄로 연결한 문자열이었다)

Final Flag

InIt{smiley_1988_teacup_3389_lisbon}
